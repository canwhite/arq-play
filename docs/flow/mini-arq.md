## 📊 流程概览

`mini_arq.py` 用 Redis List 组成简化异步任务队列：生产者创建任务并入队，Worker 在并发上限内阻塞取任务、记录处理中状态、执行已注册的异步函数，最终保存结果。生产者通过任务 ID 轮询结果；独立 reaper（回收器）会把异常滞留的处理中任务重新入队，所以整体交付语义是“至少一次”（at-least-once），不是“恰好一次”。

## 📚 概念解析

### Redis List（Redis 列表）

- **是什么**：Redis 内存里的双端列表；这里 `LPUSH` 从左侧放入任务，`BLPOP` 从左侧取出任务，因此当前实现是后进先出（LIFO）。
- **为什么需要**：像把任务便签放进共享收件箱，生产者和 Worker 可跨进程或跨机器协作。
- **怎么用**：如果业务要先进先出（FIFO），需改成一端写、另一端取；例如 `LPUSH` 配 `BRPOP`。

### BLPOP（阻塞弹出）

- **是什么**：从 Redis List 取元素；队列为空时，客户端连接等待到有任务或超时。
- **为什么需要**：不像不断 `GET` 一样频繁空查，任务到达会立即唤醒等待的 Worker。
- **怎么用**：这里 `timeout=1`，使 `run()` 最多约一秒检查一次 `_stopping`，便于正常停机。

### Semaphore（信号量）

- **是什么**：并发令牌计数器；`max_concurrent=5` 就是最多五个任务同时执行。
- **为什么需要**：像只有五个工位的车间，先占工位才从队列取任务，避免 Worker 把 Redis 任务拉到本地后堆积。
- **怎么用**：每次 `acquire()` 必须有对应 `release()`；空队列和 `_execute()` 的 `finally` 都负责归还令牌。

### In-progress record（处理中记录）

- **是什么**：任务执行前写入的 Redis key，保存 job 内容和开始时间，并有兜底 TTL。
- **为什么需要**：Worker 崩溃时，主队列已没有该任务；这条记录让回收器知道应重新投递什么。
- **怎么用**：结果写入前会删除该 key；TTL 不是成功确认，`_reaper()` 才处理已超时且仍可读到的记录。

### Reaper lock（回收锁）与至少一次投递

- **是什么**：`SET ... NX` 是“仅不存在时设置”的原子操作；第一个回收器拿到锁才可重新入队。
- **为什么需要**：多个 Worker 的回收器同时扫描时，锁避免同一滞留任务被重复回收。
- **怎么用**：任务可能在执行完成边界被重新入队，调用方应让任务实现幂等（idempotent），能安全承受重复执行。
